第二阶段已通过：Mac 生成完整备份，在独立数据库、独立 MinIO 和不同主密钥的空账号中恢复，随后同一签名包退出进程并冷启动核对；关闭来源 gRPC 与 MinIO 后再次冷启动，正文、刻度和图片仍一致。正常 `lib/main.dart` 入口的最终 Mac Debug 构建和签名检查也已通过。

## 使用方式

1. 在工作区侧栏打开“备份与恢复”，输入至少 12 个字符的备份密码并再次确认。Mac 选择保存文件夹后，应用自动生成 `印迹备份-日期-时间-随机标识.wtbackup`。保存采用同目录临时文件、写后核对及重命名，失败保留已有备份。
2. 将 `.wtbackup` 文件和密码分别妥善保管。备份密码与登录密码独立；丢失备份密码后不能从该文件找回内容。
3. 在独立服务的空账号中打开“恢复”，选择文件、输入备份密码，先核对创建时间和主题、分组、记录、图片及刻度模板数量，再点击“恢复到当前空账号”。关闭弹窗后工作区刷新。
4. 重新打开记录，核对正文、刻度、标题、级别和图片。恢复失败保留所选文件、密码及预览，可在修复原因后重试。若提示“恢复结果尚未确认”，先重新打开工作区核对，避免把已提交但响应丢失误判为未恢复。

“空账号”指六类业务表中没有该用户的主题、分组、记录、权限、文件及刻度模板，包含尚未物理移除的软删除行。恢复不会清空或覆盖目标账号；有数据、资源标识冲突或不完整备份会被拒绝。当前保留资源和图片标识，因此恢复到同一数据库中与源账号并存时会因标识冲突而拒绝；跨环境恢复使用独立数据库。

## 备份包含的内容

| 类别 | 保留信息 |
| --- | --- |
| 主题、分组 | 名称密文、数据密钥封套、层级和稳定标识、默认分组、级别筛选、视图及排序、自动冻结设置、结束时间、创建和更新时间。 |
| 记录 | 标题、`rich`、`scales`、级别的完整密文字节，正文内嵌刻度载荷、文档显示配置、所属分组及时间。 |
| 权限 | 每个主题、分组和记录的 owner 权限及包装数据密钥。导出采用实际读取所用的权限封套，缺失或不能解密时拒绝生成完整备份。 |
| 图片 | 全部有效文件元数据、原始加密媒体字节、文件标识和记录关联、包装数据密钥、IV、加密元数据、MIME、大小、时间和 SHA-256。归档名使用文件标识，避免同名冲突。 |
| 刻度模板 | 稳定标识、创建时间，以及 `v1` 模板密文与包装密钥。记录中的刻度值随正文载荷保留。 |
| 恢复材料 | 源账号的 32 字节主密钥与完整服务端归档一起在客户端加密后写入文件，不另存明文密钥。 |

导出前校验所有内容和图片能用恢复材料解密，检查图片摘要与正文中的 `file:<UUID>` 引用。旧版外链、本地图片、缺失媒体或不支持的刻度模板会使备份明确失败，需修复或重新上传后重试；不会静默省略并显示成功。旧“配置 ZIP”、TXT、PDF 和内容导出不能替代 `.wtbackup`。

本阶段顺带修正图片链路的两个实际缺陷：同一记录内同名上传改用不同对象路径，避免互相覆盖；可选 IV／加密元数据为空时写入空字节，避免 PostgreSQL `NOT NULL` 失败。图片拥有者写入及下载／删除校验统一使用认证后的内部用户标识。

## 格式与恢复行为

服务端归档是版本化 ZIP，固定 `backup.json` 清单与 `media/<文件标识>.bin`，仅接受普通 Store 条目。清单含版本、备份标识、来源用户、创建时间、完整关系和媒体摘要。服务端使用 PostgreSQL repeatable-read 快照读取元数据，任何媒体读取或核对失败均使后台任务失败。后台下载仍只是密文归档，缺少客户端保护的主密钥，不能单独作为便携恢复文件。

客户端文件结构为 `WTBACKUP` 标识、版本 1、16 字节随机 salt、12 字节随机 nonce、AES-256-GCM 密文及 16 字节认证标签。加密载荷包含源主密钥和 ZIP，整个头部作为认证附加数据。密码通过 PBKDF2-HMAC-SHA-256、600000 次迭代生成 256 位密钥，运算在独立 isolate 执行。参数与算法用法参考 [OWASP 密码存储指南](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)及 [cryptography 官方 API](https://pub.dev/documentation/cryptography/2.9.0/cryptography/)。这不等同于完整安全审计。

恢复时先在本地验证密码、认证标签、媒体摘要和解密能力，然后用源主密钥解开每个数据密钥，重新包装到目标账号现有主密钥下。正文、图片和模板内容密文不重写；目标主密钥不被源主密钥替换。密码及源主密钥不上传服务端，不依赖旧账号登录 Cookie、旧数据库、旧媒体地址或旧 Mac 钥匙串。

服务端先验证所有条目、关系、大小、密钥形态和摘要，再在一个事务内检查目标为空及标识无冲突。媒体写入唯一恢复路径，元数据统一绑定到目标认证用户并事务提交。失败时先用独立上下文确认媒体没有被已提交元数据引用，再进行补偿删除；数据库无法确认或发现已提交引用时保留媒体并报告结果不确定，避免提交确认丢失后误删有效图片。清理失败会明确报告。

当前单份服务端 ZIP 上限为 256 MiB，记录／文件条目上限 50000，导入按 64 KiB 分块；密码保护层另有少量固定开销。限制在客户端与服务端均检查。当前导入在上传媒体期间持有六张业务表的写入互斥锁，适用于当前小规模自用；大账号、并发恢复和分段异步恢复尚未验收。

Mac Debug 增加“用户选定文件读写”权限，保留 App Sandbox。Mac 选择文件夹是为了授权其子文件的临时写入和重命名，并未添加全盘访问。范围依据 Apple 的 [App Sandbox 文件访问说明](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)。Profile／Release 钥匙串配置沿用第一阶段，未扩大其验收结论。

## 验证边界

- 本轮使用真实 PostgreSQL、Redis、MinIO、JWT／Redis 认证及 Mac Debug 程序；合成身份通过测试入口注入，未覆盖完整 HTTP 注册／登录流程。
- 不包含增量备份、非空账号合并或覆盖、自动备份计划、软删除历史恢复、旧配置 ZIP 迁移和 256 MiB 以上备份。
- 旧版外部图片或不支持的加密载荷明确拒绝备份，需要先修复数据；没有假定历史缺件已经找回。
- Profile／Release 签名及 Data Protection Keychain、跨重新签名授权、VoiceOver、其他平台／设备、长期稳定性与性能仍需分别验收。
- 本次没有修改 `.proto`、生成协议代码或数据库表结构。复用现有全量导出后台任务与流式导入 RPC，将旧模拟恢复流程替换为完整账号恢复。
